## Problem Statement

Designers collect references that "look nice" but can't search them by *how* they work visually. Pinterest and moodboards sort by subject or aesthetic ("Y2K", "surrealism"). This tool sorts graphics, posters and illustrations by **formal visual language**: line, shape, color, value, balance, movement and so on.

Inspiration: an art-direction teacher's reel ("A Taxonomy of Visuals") showing references classified by the mechanism behind the image, not the aesthetic, and rendered as an animated web of nodes with image thumbnails as leaves.

## What Makes This Cool

- **The graph rearranges itself.** Pick a filter (e.g. *Line*) and every thumbnail drifts into a web of clusters: straight-line images group together, then shade toward jagged, then curved, then implied. Switch to *Value* and they flow into a high-key ↔ low-key gradient.
- **It's honest about what it knows.** Every score is either *measured* (pixel math) or *perceived* (vision model), and the demo shows per-feature accuracy against hand labels.
- **It learns your eye.** Every correction you make is saved as training data. Stretch goal: train small probes so the scoring becomes yours.

## Constraints

- 36-hour hackathon, solo builder, laptop (Apple Silicon assumed).
- Input: 2D still images only (posters, graphics, illustrations, photos). No 3D files.
- **No LLM in the scoring path** (user preference: LLMs feel unreliable; wants numeric, deterministic outputs).
- Must have a real database that stores the images.
- Demo must survive bad venue wifi. The batch path must work offline once models are cached.

## Premises (agreed)

1. **Fixed seed taxonomy you write**, not unsupervised clustering. Categories and sub-classes are rows loaded into the DB before any images exist ("seeding").
2. **Every image gets one score per sub-class.** Scores come from pixel math (measurable features) and SigLIP 2 text-prompt similarity (perceptual features). No LLM.
3. **Spectrum categories store one continuous value.** They make the cleanest gradients.
4. **Supabase** (Postgres + pgvector + Storage) is the single database: image files, scores, embeddings, corrections, and the taxonomy graph as tables. No separate graph DB.
5. **Corrections are saved from hour 1.** Probe training on DINOv2 embeddings is a stretch goal / v2.
6. **Validation gate:** only categories that agree with ~50 hand-labeled images (≥75%) appear in the demo. The rest stay in the DB, hidden.

## Feature Taxonomy (seed)

Type key: **S** = spectrum (one continuous value, 2 anchors), **T** = tags (score per sub-class, N anchors).
Method key: **PX** = pixel math (OpenCV/numpy), **SL** = SigLIP 2 zero-shot text prompts, **SAL** = saliency map.

| Category | Type | Sub-classes (anchor order) | Primary method |
|---|---|---|---|
| Line | T | Straight → Jagged → Curved → Implied | PX (Hough lines, contour curvature, corner density) + SL (implied) |
| Shape | T | Rectangle → Triangle → Circle → Organic | SL + PX (contour approximation) |
| Form* | T | Geometric → Organic → Open | SL (images that *depict* volume) |
| Space | S + T | Shallow ↔ Deep; + Negative-space dominant | SL (depth) + PX/SAL (empty-area ratio) |
| Color | S + T | Warm ↔ Cool; + Complementary, Monochromatic | PX (hue histogram, 180° peaks, hue spread) |
| Value | S | High-key ↔ Low-key | PX (mean luminance, histogram) |
| Texture | S | Smooth ↔ Detailed/Rough | PX (Laplacian variance, high-frequency energy) |
| Balance | T | Bilateral → Radial → Asymmetrical | PX (mirror/rotation SSIM) + SL (asymmetrical) |
| Contrast | T | Value → Color → Scale | PX (value, color) + SL (scale) |
| Emphasis | T | Centered → Isolation → Convergence | SAL (centroid, isolation) + SL (convergence) |
| Movement | T | Diagonal → Directional → Swirling | PX (edge-orientation histogram) + SL |
| Rhythm & pattern | T | Regular → Alternating → Progressive | PX (FFT/autocorrelation peaks) + SL |
| Unity & variety | S + T | Minimal ↔ Chaotic; + Harmonious | PX (edge density, entropy, palette spread) |

\*Form is kept in the seed for illustrations that depict volume; expected to fail the validation gate on flat graphics. Fold into Shape if so.
**Cut:** Proportion & scale (physical size of the artwork can't be read from a 2D file; "scale contrast" covers in-image scale).

### How SigLIP scores work (no LLM)
- For each sub-class, write 3–5 descriptive prompts (prompt ensemble), e.g. Line/Jagged: "a graphic made of sharp zigzag lines", "an illustration with jagged angular strokes".
- Embed the prompts once with the SigLIP 2 text encoder and the image with the image encoder. Score = mean cosine similarity across that sub-class's prompts.
- **Normalize per sub-class across the whole collection** (z-score, then sigmoid or rank-percentile). Raw CLIP/SigLIP similarities are compressed into a narrow band, and normalizing spreads them out.
- Within a tag category, apply a softmax across sub-classes (temperature tuned on hand labels) so anchor weights sum to 1.
- Combine with pixel-math scores as a weighted average per sub-class. Weights are set by which source agrees better with the hand labels.

## Data Model (Supabase)

```sql
-- seed tables (written by hand, loaded once)
create table categories (
  id text primary key,            -- 'line', 'value', ...
  name text, kind text check (kind in ('spectrum','tags')),
  enabled boolean default false,  -- flipped on by the validation gate
  sort int
);
create table subclasses (
  id text primary key,            -- 'line.jagged'
  category_id text references categories,
  name text, definition text,
  prompts text[],                 -- SigLIP prompt ensemble
  anchor_order int                -- position around the ring (gradient order)
);

-- filled by the pipeline
create table images (
  id uuid primary key default gen_random_uuid(),
  storage_path text not null,     -- Supabase Storage bucket 'images'
  thumb_path text not null,       -- 256px thumbnail in the same bucket
  sha256 text unique not null,    -- dedupe on re-ingest
  width int, height int, source_url text,
  created_at timestamptz default now(),
  siglip vector(1152),            -- SigLIP 2 so400m image embedding
  dino   vector(768),             -- DINOv2 ViT-B/14 embedding (neighbors + future probes)
  metrics jsonb                   -- raw pixel measurements, for debugging/hover
);
create table scores (
  image_id uuid references images on delete cascade,
  subclass_id text references subclasses,
  value real,                     -- 0..1 after normalization
  source text,                    -- 'pixel' | 'siglip' | 'combined' | 'probe'
  primary key (image_id, subclass_id, source)
);
create table corrections (        -- your labels: hand-label set + UI fixes
  id bigserial primary key,
  image_id uuid references images on delete cascade,
  subclass_id text references subclasses,
  label text check (label in ('absent','present','dominant')),
  created_at timestamptz default now()
);
create index on images using hnsw (siglip vector_cosine_ops);
create index on images using hnsw (dino vector_cosine_ops);
```

The "graph" is categories → subclasses → scores → images. No graph database needed.

### Extraction walkthrough (one image)
1. **Load + store:** read the file, compute SHA-256, upload original + 256px thumbnail to Storage, insert the `images` row.
2. **Normalize for analysis:** resize to 512px on the long side, convert to grayscale (luminance), HSV and LAB copies.
3. **Pixel math → `images.metrics` (raw) and `scores` (source='pixel'):** e.g. mean luminance → Value; hue histogram → Warm/Cool/Complementary/Monochromatic; Laplacian variance → Texture; mirror-SSIM → Bilateral; Hough lines + contour curvature → Straight/Curved/Jagged; edge-orientation histogram → Diagonal; FFT peaks → Regular rhythm; saliency map → Centered/Isolation/Negative space.
4. **SigLIP 2 → `images.siglip` and `scores` (source='siglip'):** one image embedding; cosine similarity against each sub-class's precomputed prompt embeddings.
5. **DINOv2 → `images.dino`:** embedding for neighbors and future probes. No scores yet.
6. **Combine (after the whole batch):** normalize each sub-class across the collection (rank-percentile), weighted-merge pixel + SigLIP into `scores` (source='combined'), softmax within tag categories. This step reruns over all images whenever new ones arrive, because normalization depends on the collection.
7. **Layout prep:** UMAP of enabled combined scores for the "All" view, stored per image.

## Layout: the web of clusters

- **Anchor layout (RadViz-style):** when a category is selected, its sub-classes become anchor points on a ring (in `anchor_order`, so neighbors are similar). Each image's target position is the score-weighted average of anchor positions, so pure examples sit at an anchor and mixed ones land between anchors. That's the gradient.
- **Spectrum categories:** two anchors at opposite ends, which gives a straight gradient. Optionally use a second spectrum as the y-axis.
- **d3-force simulation** on top: `forceX/forceY` toward the target (strength ~0.1), `forceCollide` on thumbnail radius, and link forces to each image's k=4 nearest neighbors *within the selected category's score vector*. The faint links form the web.
- **Filter switch:** recompute targets and reheat the simulation (alpha 0.6), and images drift to their new spots.
- **Default "All" view:** UMAP of the concatenated enabled score vectors (computed in Python, stored per image).
- **Rendering:** PixiJS (WebGL) sprites for thumbnails (256px), with edges in a separate Graphics layer. SVG won't hold 150+ moving images smoothly.

## Approaches Considered

### Approach A: Offline pipeline + static explorer
A Python batch script scores a folder and writes to Supabase. The Next.js app reads and animates. Effort S, risk low. No live upload.

### Approach B: Next.js + FastAPI inference service + Supabase
Same pipeline exposed as `/upload`: a new image is scored live and flies into the graph. Effort M, risk medium.

### Approach C: All in-browser (transformers.js + WebGPU)
No backend, smaller models, WebGPU quirks. Effort M-L, risk high for 36h.

## Recommended Approach

**Approach A is the deliverable. Live upload (B) is a stretch goal.** The scoring pipeline is one Python module (`score_image(path) -> metrics, scores, embeddings`) called by the batch script now and by a FastAPI `/upload` endpoint later if time allows. Nothing in A needs to change to add B.

### Image storage (required)
Every image lives in the database, never only on disk:
- **The file** goes in the Supabase Storage bucket `images` (Supabase's file store, managed alongside the Postgres DB, with access control from the same project).
- **The row** in `images` holds the Storage path, dimensions, source URL, raw pixel metrics, and both embeddings.
- **Thumbnails** (256px) are generated at ingest and stored in the bucket under `thumbs/`, so the graph loads fast.
- Storing raw bytes inside Postgres (`bytea`) was considered and rejected: it bloats the DB, slows queries and backups, and Storage gives CDN URLs the front end can load directly.
- The batch script is idempotent: it hashes each file (SHA-256, stored as `images.sha256`, unique) and skips images already ingested.

### Stack
- **Backend:** Python 3.11, `uv`, FastAPI, OpenCV, numpy, scikit-image (SSIM), `transformers` + `torch` (MPS) for SigLIP 2 (`google/siglip2-so400m-patch14-384`; fall back to `siglip2-base-patch16-224` if slow) and DINOv2 (`facebook/dinov2-base`), `umap-learn`, `supabase-py`.
- **Saliency:** spectral-residual saliency (OpenCV contrib) for speed. U²-Net only if time allows.
- **Frontend:** Next.js (App Router), PixiJS v8, d3-force, Supabase JS client, Tailwind.
- **DB:** Supabase project (Postgres + pgvector + Storage bucket `images`).
